# RAC Research Release Format (v1.0.0 draft)

**Status:** DRAFT — freeze before the first external release is cut.
**Scope:** the canonical on-disk layout of a research release bundle
`RAC-EXP-YYYY-NNN/`, its content addressing, immutability and append rules,
and its verification procedure.
**Implementation:** `release_format.py` (stdlib-only, plus
`ruthless_pipeline.certification.experiment` for the pipeline stage names).

---

## 1. Purpose & Scope

A research release packages **one closed experiment** — a single
`ExperimentArtifact` lineage (candidate → generation → optimization_telemetry
→ calibration_profile → sku → physical_session → certificate, per
`ruthless_pipeline/certification/experiment.py`) — into a content-addressed,
self-describing directory tree suitable for archival, independent replication,
and direct use as a paper dataset.

A release is the **exportable, self-contained projection of one
`ExperimentRegistry` entry** (§7). The registry is the live, append-only index
inside the repo; the release is the frozen, transportable copy that resolves
without any repo context.

**What this document freezes:**

- The directory layout and the role of each top-level file (§2).
- Naming and identifier rules (§3).
- Content addressing: every artifact referenced by 64-hex SHA-256; the
  release's own `content_hash` computed over `MANIFEST.json` (§4).
- Immutability and post-freeze append rules with a revision log (§5).
- The verification procedure (§6).

**What this document explicitly does NOT claim:**

- No claim about experimental validity. A release that verifies cryptographically
  may still describe a failed or invalid experiment (see `FAILURE.json`, §2).
- No claim of completeness of the underlying evidence. Stage subdirectories may
  be absent if the corresponding stage is absent from the experiment's lineage.
- No guarantee that the bundle contains the large binary payloads themselves when
  a stage artifact is referenced by external URI; in that case the manifest
  still pins the payload's SHA-256 (§4).

## 2. Directory Layout

```
RAC-EXP-2025-001/
├── experiment.json          # ExperimentArtifact (schema per experiment.py)
├── MANIFEST.json            # SHA-256 for every file in the bundle (§4)
├── RELEASE.json             # release metadata (§3)
├── REVISIONS.json           # append-only revision log (§5)
├── REPORT.md                # human-readable report, generated by report_compiler
├── FAILURE.json             # OPTIONAL failure record (§2.4)
└── stages/
    ├── candidate/           # immutable artifacts of the candidate stage
    ├── generation/
    ├── optimization_telemetry/
    │   └── outcome/         # held-out outcome appends land here (§5)
    ├── calibration_profile/
    ├── sku/
    ├── physical_session/
    └── certificate/         # certificate stage additions land here (§5)
```

### 2.1 `experiment.json`

The `ExperimentArtifact` for this experiment, serialized as its `to_dict()`
JSON. It MUST pass `ExperimentArtifact.validate()`: `experiment_id` matches
`RAC-EXP-YYYY-NNN` and equals the directory name; required stages
(`candidate`, `generation`) are present; present stages appear in pipeline
order; every `StageRef.sha256` is a 64-hex digest. Each `StageRef.sha256` MUST
equal the digest recorded in `MANIFEST.json` for the corresponding file under
`stages/<stage>/` (or the digest of the externally hosted payload when
`StageRef.uri` is set).

### 2.2 Stage subdirectories

`stages/<stage>/` holds the immutable artifacts produced by that pipeline
stage, at stable relative paths. Subdirectories exist only for stages present
in `experiment.json`. Stage artifact files are **write-once**: after the
initial freeze they may not be modified, renamed, or deleted (§5).

### 2.3 `REPORT.md`

Generated by `report_compiler`; never hand-edited after generation. It is a
rendering of `experiment.json` plus the stage artifacts — not a source of
truth. Hash-pinned like every other file, so any hand edit is detected (§6).

### 2.4 `FAILURE.json` (optional)

Present iff the experiment closed as a failure. Required fields:
`failure_stage` (one of the pipeline stage names), `failure_reason`
(free text), `detected_utc` (ISO-8601), and `invalidates` (list of downstream
stages whose artifacts must be disregarded). A release with `FAILURE.json` is
still a valid, verifiable release — failure records are data, not an error
state of the bundle.

## 3. Naming, Identifiers, and Release Metadata

- **Release id / directory name:** `RAC-EXP-YYYY-NNN` — the `experiment_id`.
  One release per experiment; the id is unique across all releases.
- **Timestamps:** ISO-8601 UTC, `YYYY-MM-DDTHH:MM:SSZ`.
- **Digests:** lowercase 64-character hex SHA-256 everywhere.

`RELEASE.json` carries the release metadata:

| Field | Rule |
|---|---|
| `release_id` | equals `experiment.json.experiment_id` and the directory name |
| `created_utc` | ISO-8601 UTC timestamp of the initial freeze |
| `source_commit` | full 40-hex Git commit of the repo that produced the release |
| `content_hash` | 64-hex SHA-256 over `MANIFEST.json` canonical JSON (§4) |

`RELEASE.json` is written at freeze time and is itself listed in
`MANIFEST.json`. Because `content_hash` is computed over the manifest, the
order of operations at freeze time is: (1) build manifest over all content
files, (2) compute `content_hash`, (3) write `RELEASE.json`, (4) rebuild and
write `MANIFEST.json` so that it also pins `RELEASE.json`, (5) record the
freeze in `REVISIONS.json` and rebuild the manifest a final time. The shipped
`release_format.py` test suite demonstrates this seal procedure
(`test_full_round_trip_build_seal_verify_copy`).

## 4. Content Addressing

- **Every file** in the bundle — stage artifacts, `experiment.json`,
  `REPORT.md`, `RELEASE.json`, `REVISIONS.json`, `FAILURE.json` if present —
  is listed in `MANIFEST.json` as `"<posix relative path>": "<sha256>"`.
  `MANIFEST.json` is the only file not listed in itself.
- **Stage references:** every `StageRef.sha256` in `experiment.json` is a
  64-hex digest resolving to a manifest entry (or to an external payload when
  `StageRef.uri` is set). No artifact is ever referenced by name alone.
- **`content_hash`:** `SHA-256(canonical_json(MANIFEST.json))`, where
  canonical JSON means UTF-8, sorted keys, `(",", ":")` separators — the same
  canonicalization used by `ExperimentArtifact.lineage_hash` and
  `PatternManifest.manifest_sha256`. Implemented as
  `release_format.compute_content_hash`. The `content_hash` is the single
  value to cite when referencing this release externally; any change to any
  file changes it.

## 5. Immutability and Append Rules

At `created_utc` the release is **frozen** (revision 0 in `REVISIONS.json`).
Thereafter the bundle is immutable with exactly two exceptions:

1. **Held-out outcome appends** — new files under
   `stages/optimization_telemetry/outcome/`. This permits publishing a
   preregistered release before the held-out run completes, then appending
   the outcome without touching anything already sealed.
2. **Certificate stage additions** — new files under `stages/certificate/`
   plus the certificate `StageRef`, since the certificate necessarily
   post-dates the physical session it attests.

Enforcement is **by stage name** (`release_format.ReleaseRevisionLog`):
post-freeze, only `optimization_telemetry` and `certificate` appends are
accepted; an append touching `candidate` (or any other stage) is rejected.
Every allowed append bumps the revision log: `REVISIONS.json` gains one
`{revision, stage, created_utc, action: "append", detail}` entry with a
strictly sequential revision number, and `MANIFEST.json` is rebuilt to cover
the new files (changing `content_hash`; prior revisions remain recoverable
from the log plus prior manifests retained by the archivist).

`REVISIONS.json` is itself append-only: `ReleaseRevisionLog.from_json`
rejects non-sequential revisions, a second freeze, and any post-freeze entry
outside the appendable stage set — including hand-edited logs.

## 6. Verification Procedure

`release_format.verify_release(directory)`:

1. Require `MANIFEST.json`; parse and validate every entry (safe relative
   POSIX path, 64-hex digest).
2. Walk the directory; hash every file except `MANIFEST.json`.
3. Compare sets and digests, classifying each discrepancy as:
   - **tampered** — listed and present, digest differs;
   - **missing** — listed, absent;
   - **extra** — present, unlisted.
4. `ok` iff all three sets are empty. Additionally, verifiers SHOULD check
   that `experiment.json` validates, that each `StageRef.sha256` resolves to a
   manifest entry, and that recomputing `compute_content_hash` over the
   on-disk manifest reproduces `RELEASE.json.content_hash`.

A release that fails verification MUST NOT be cited as evidence for any claim.

---

## 7. Relationship to the ExperimentRegistry

The `ExperimentRegistry` (in-repo, append-only, keyed by `experiment_id` and
`lineage_hash`) is the live index of experiment lineages. A release is the
**exportable, self-contained projection of exactly one registry entry**:

- `experiment.json` is byte-for-byte the registry entry's `to_dict()` JSON;
  the registry's `lineage_hash` is therefore reproducible from the release.
- The stage artifacts the registry references by `(artifact_id, sha256)` are
  materialized under `stages/<stage>/`, so the release resolves without the
  repo, the registry, or network access (except URI-referenced payloads, §4).
- Export direction is one-way: registry → release. Releases are never
  re-imported; divergence is caught by comparing `lineage_hash` and
  `content_hash` against the registry record.

## 8. Reference Implementation

`release_format.py` provides:

| API | Behavior |
|---|---|
| `ReleaseManifest.build(directory)` | walks the tree, hashes every file, produces the manifest |
| `ReleaseManifest.write(directory)` | writes `MANIFEST.json` |
| `compute_content_hash(manifest)` | SHA-256 over the manifest's canonical JSON |
| `verify_release(directory)` | re-hashes; reports ok / tampered / missing / extra |
| `ReleaseRevisionLog` | append-only revision log enforcing the §5 rules by stage name |

Tests: `test_release_format.py` — manifest build and content-hash determinism,
tamper/missing/extra detection, append-rule enforcement (candidate-stage
modification rejected post-freeze; outcome append allowed), JSON round-trips,
and the full seal-copy-verify round trip.
